# Known limitations (Phase 1)

Things that work differently from what you might expect, or are deliberately not built. None of these block the Definition of Done.

## By design (out of scope for Phase 1)
- **No connectors and no live values.** No BACnet/Modbus/MQTT code exists. Records have no `cur` or `curVal`; Site Organization shows the latest *history* sample and says so.
- **Editing is limited to sites, equipment and points.** Spaces, systems, devices and other kinds of record are not shown in the tree and cannot be created or edited there (tags on a record can be edited, whatever kind it is). The Trend Viewer never writes; a test checks writing code exists only in the Site Organization edit folder.
- **No rules, sparks, alarms, dashboards, reports, user management or multi-tenant features.**
- **No mobile polish.** The layout is usable on a tablet or phone (nothing overflows, the chart comes first, the picker sits below) but it is designed for a desktop browser.

## Editing (Site Organization)
- **No permissions model.** Anyone who can sign in can add, edit, move and delete. The sign-in user is Haxall's `su` account.
- **Deletes are permanent** and take the stored history with them (history is in memory, so a restart also loses it). There is no undo or recycle bin.
- **Demo data is regenerated by `make load`.** Edits to demo records are lost then, and records you attached to demo equipment point at records that no longer exist (the spec badge reports them). Sites you create are left alone.
- **Equipment types:** templates exist for AHU, VAV, main meter and submeter. Any other standard type can be created, but its points must be added by hand.
- **Deleting equipment other records link to** (VAVs that point at an AHU, submeters that point at a meter) offers to remove those links; if you decline, they show "does not exist" problems.
- **Another person's edit wins safely:** a save is refused if the record changed after you opened it (you reload and redo it). Several people editing the same record at once is not otherwise coordinated.
- **Units are looked up at save time** and stored in Haxall's spelling ("h" becomes "hr", "s" becomes "sec").
- **New points have no data.** They are created with history switched on, but nothing writes to them until a connector (Phase 2) or a script does.
- **Records created by hand carry `hisMaxItems`** (a Haxall-only tag, 20,000 by default) on points with history, like the demo points. Remove it when moving records to SkySpark.

## Haxall behaviour you will notice
- **History lives in memory only.** Restarting Haxall (or its container) empties every history. Records (site, equipment, points) survive. `make up` and `make specs` reload the demo data automatically; anything else that restarts Docker needs `make load`.
- **Each point keeps a limited number of samples** (`hisMaxItems`; Haxall's default is 1000, the demo sets 20,000, about 200 days at 15 minutes).
- **History numbers are 32-bit floats** (about 7 significant digits). Values are shown rounded to 7 digits.
- **No server-side rollups.** Haxall has `hisRead` and `hisWrite` only (no `hisRollup`). The Trend Viewer thins data for display itself and keeps exact values for the tooltip, table and CSV.
- **New or edited spec files need a Haxall restart** (`make specs` does it). Haxall reads the library folders once at startup.
- **Pinned to a specific Haxall source commit** (master of 15 Oct 2026, reports 4.0.6), not a release tag, because the features used (`validate()`, `instantiate()` graphs) were read from master. Rebuilding with newer commits is a deliberate step (see `.env.example`).
- **The first Docker build takes several minutes** (it compiles Fantom, Xeto and Haxall). Later starts are quick.
- **Haxall has no cross-origin support.** The browser talks to Haxall through the dev server. A production build needs a proxy in front of it (not set up).

## The demo data
- **Dates are relative to the moment you load.** The 90 days end "now" (rounded to 15 minutes). Fault dates therefore move on every load; `faults.json` has the exact times.
- **Simplified building physics.** Occupancy is 6am-6pm on weekdays (no holidays), weather is a smooth seasonal curve plus a daily cycle, and the control logic is intentionally simple. The data is realistic enough to look like a building, not a calibrated model.
- **Simulated sensor faults do not feed back into control**; they alter only the recorded values.
- **VAVs are siblings of AHUs in the tree.** They reference their AHU with `airRef` (a "fed by" link), not `equipRef` ("contained in"), which is the Haystack 4 convention. Nesting by `equipRef` works for data that uses it.

## Specs
- **The `ats` namespace is not registered** at xeto.dev. Fine locally; register or rename before publishing the library.
- **`ats::AtsOccupiedSp`** exists because `ph` has no concrete AHU occupancy point (only the zone version).
- **Point checks on an equip are cached for 30 seconds**, so adding or removing a point can take that long (or a page reload) to change the equip's badge.
- **Spec problems on a point show on the point and its tree row**, not on its parent equip (the equip badge checks which required points exist).

## Trend Viewer
- **At most 10 points** at a time (the 9th and 10th reuse the first two colours as dashed lines). The reference palette has 8 colours; a 9th distinct hue is deliberately not generated.
- **"Last N days" is rolling from now**, so if the demo data was loaded some time ago, "Today" may be empty; use *All data*. Weeks start on Monday.
- **Colour contrast:** three of the eight light-mode colours (aqua, yellow, magenta) are under 3:1 against a white background. That is why every series is also named in the legend, the tooltip and the table.
- **Axis ticks** are chosen by the chart library and sometimes look uneven on long ranges.
- **Hover/zoom were tested in a Chromium-based browser** (the app's own pane and headless Brave). Other browsers should work but were not tried.

## Look and feel
- **Ubuntu is bundled for the Latin and Latin-extended alphabets only** (regular, medium, bold). Text in other alphabets, and symbols Ubuntu does not have, are drawn in the system font. Other alphabets can be added in `ui/src/main.tsx`.
- **The ATS logo is a PNG copied from the ATS website** (white on transparent, 900x450). It is used on navy only and may look soft on very high-resolution screens.
- **Dark mode follows the operating system**; there is no switch inside the app.
- **Only the chart colours were re-derived** (four of eight now use ATS hues); brand navy and gold are not chart colours because they are too dark or too light to read as thin lines. See `docs/design-system.md`.

## Tooling and platform
- **Developed on macOS (Apple Silicon).** The Makefile needs a Unix shell. Windows (without WSL) and Linux were not tried; the Docker build is multi-architecture and should work on Intel.
- **Node 24** is required (the tools run TypeScript directly with Node's built-in type stripping).
- **Passwords:** the demo uses a single `su` account whose password is in `.env` (never committed). The app talks plain HTTP to `localhost`; it is not set up for use over a network, and Docker only lets this computer reach Haxall (other machines on the same network cannot). `make up` will not create a new database while the password is still the example `change-me`.
- **Changing `HAXALL_SU_PASSWORD` in `.env` later does not change an existing database's password.** It is applied only when the database is first created (use `make reset`).
- **No git repository yet**, as agreed. `.gitignore` and `.env.example` are ready for it.
